# Consumer UI v0.18 — Korea first, sharp photos

This document covers the public app (`site-public-cleared/`, `client/`) for v0.18. It follows the operator's fourth brief and
the v0.18 addendum of `docs/STATIC_ARCHIVE.md`:

1. A Korean media façade and media art platform first. Foreign cases get their own section and stay fully searchable.
2. Sharp, high-resolution photos of the actual project with its media running. A small thumbnail never fills a large
   slot.
3. A professional architecture and digital-museum design.

The same dataset holds Korea and the world. Only the structure and the priority of the screens differ.

## Menu and routes

| menu item | route | phone tab bar |
|---|---|---|
| 홈 | `#home` | 홈 |
| 국내 미디어파사드 | `#korea`, `#korea/<kr_region>` | 국내 |
| 국내 미디어아트·전시 | `#programs` | — (top-bar menu; the 국내 tab lights up) |
| 지도 | `#map` (국내), `#map/world` (세계) | 지도 |
| 세계 미디어파사드 | `#world` | 세계 |
| 아카이브 검색 | `#explore` | — (top-bar search button) |
| 내 컬렉션 | `#saved` (tabs: 장소, 코스, 기록) | 컬렉션 |

How each screen size shows the menu:

- Desktop (1024 px and wider): the sidebar lists all seven items.
- Tablet (768–1023 px): the rail lists all seven, with short labels.
- Phone: the bottom bar keeps five tabs. The top bar has the search button (아카이브 검색) and a menu button (전체
  메뉴). That menu lists every section plus 마이, 연구 데이터, 설정 and 지원.
- Below 1024 px a tab shows its short label. Its accessible name is still the full section name.

`#my` (settings, account, data) is reached from the avatar on wider screens and from the menu on a phone.

Places are split into the two Korean sections by project type (`catalog.js` `sectionOf`):

| section | project types |
|---|---|
| 국내 미디어파사드 | `media_facade`, `projection_mapping`, `urban_screen`, `media_wall` |
| 국내 미디어아트·전시 | everything else: `light_art`, `festival_program`, `interactive_installation`, `media_architecture`, `other`, and no type at all |

A place page lights the menu item of its own section. A foreign place lights 세계.

Links that carry a dataset id without the app's `AR-` prefix open the project, for example `#place/CAT-14IPYSX`. This is
the form the live check uses.

## Korean regions

`kr_region` is one of `seoul`, `gyeonggi_incheon`, `gangwon`, `daejeon_sejong_chungcheong`, `gwangju_jeolla`,
`daegu_gyeongbuk`, `busan_ulsan_gyeongnam` or `jeju`.

- The app takes the dataset's value whenever the field exists, in index rows and in records. A `null` value stays
  unknown.
- Only when a dataset has no such field at all (before v0.18) does the client derive the region from the city or the
  address. It does this with the gazetteer in `archive-taxonomy.js`: `krRegions`, `krRegionOf`, `krRegionLabel`.
  - The gazetteer is kept apart from `vocab`, so the pipeline's own `kr_region` vocabulary can sit next to it.
  - The first place name in the text wins: 경기도 광주시 is Gyeonggi, 광주광역시 is Gwangju.
  - Ambiguous names, such as 고성, stay unknown.
- Curated and synced Korean places have no field, so they are always derived.

## Search, filters and the map

- **Archive search (`#explore`).** With no country chosen, Korean results come first and none are dropped:
  - When browsing, and under every explicit sort, the list is strictly Korean first. Each group keeps the chosen order,
    under the headings 국내 N곳 and 해외 M곳.
  - A keyword search ranked by relevance keeps the best match on top: an exact foreign name still leads. Korean results
    lead among equally good matches (`KR_BOOST` in `catalog.js`). In this mode the list has no group headings.
  - Choosing a country lists only that country.
- **Filters.** The filter panel has a 국내 지역 facet (`kr_region`) and the world region and country facets. The name of a
  Korean region also finds its projects in a search.
- **Map (`#map`).** The map opens on the 국내 view: Korean results only, framed on the peninsula. A switch (국내 · 세계)
  changes to `#map/world`, which shows every result.
  - In both views the pins, the list under the map and its count come from one list (`mapProjects()`).
  - The note "N곳은 목록에서만" counts the places in the same view that have no coordinates.
- **`#world`.** This page has its own world map:
  - The four zoom-1 OpenStreetMap tiles, cropped to 78°N–58°S and toned for night, with a dot per group of nearby
    projects that have coordinates.
  - It is credited, loaded lazily, and links to the interactive `#map/world`.
  - The list is filtered by world region and country chips, and the count is always the list.
- **Search scope (한국 · 세계 · 전체).** A segmented control above the results, each option with its count for the
  current query and filters.
  - Until the visitor picks one, the scope is automatic. It follows where they came from: a Korean section, the Korean
    map or a Korean project gives 한국; the world section, the world map or a foreign project gives 세계. Otherwise it
    follows the query: Hangul gives 한국, anything else 전체.
  - If an automatic scope finds nothing for a query while the whole archive has results, it widens to 전체 and says so
    ("한국에는 결과가 없어 전체에서 찾았어요").
  - A picked scope stays while typing. It goes back to automatic on 모두 지우기 or on entering the search again.
  - A chosen country overrides the scope. The map ignores the search scope and keeps its own 국내 · 세계 switch.
- **Forgiving search** (`catalog.js`, no external service). Each word is matched:
  - in the place's search text without spaces ("동대문디자인" finds "동대문 디자인");
  - for Hangul, as jamo (NFD), so a syllable still being typed ("롯데워", "롯데월ㄷ") matches;
  - only when nothing matches exactly: at edit distance 1 (one letter added, dropped, changed, or two neighbours
    swapped) from a word of the archive, a name written without spaces, or the start of one. Latin words need 4 letters
    and Hangul words 5 jamo; words with digits are never guessed.

  A guess is reported ("‘electornica’와 똑같은 기록이 없어 비슷한 ‘electronica’(으)로 찾았어요"), and a guessed word
  found in a name ranks like a name match. At 5000 projects a search with a guess takes about 37 ms the first time
  (building the word list) and 5 ms after that.
- **시·군·구 inside a Korean region (`#korea/<region>`).** Chips with counts come from the places' own `city_ko` (or
  the city's Korean name) and `district`; nothing is estimated.
  - A region whose places are all in one city (서울) goes straight to its districts (구·군). Otherwise it shows cities
    (시·군) first, then the districts of the chosen city when any are known.
  - Places without the value count under 위치 미상, so the chips always add up to the region.
  - A region without projects says so, offers no chips, and links to the archive search; its tile reads 0개 프로젝트.
  - The reader takes `city_ko` and `district` from index rows when the pipeline adds those columns. Today only full
    records and the curated places carry them.

## Home (`#home`)

The home page reads `data/home.json` only: no index or shard on the first paint (checked by `qa/v18.spec.mjs` and by the
pipeline's verify-live `home_loads_index`). Its sections, in order:

1. **Hero.** Korean flagship photos with the media running. A slide needs all of these:
   - a reviewed photo: v0.18 tier 1 or 2 and `approved: true`; in a v0.17 home.json, tier 1;
   - a largest rendition of at least 1600 px.

   If there is no Korean slide, the hero shows the single best reviewed photo from elsewhere. If there is none at all,
   it shows the generative LED graphic, which says it is a graphic.

   Slide behaviour:
   - The first slide is `fetchpriority=high` and not lazy; the others are lazy.
   - Every slide is `decoding=async`.
   - `sizes` follows the hero box: on a portrait screen the photo covers the height.
   - Credits are author · licence · provider, linked to the file page.
2. **국내 지역.** Eight tiles with counts and a photo. Without a large enough photo a tile shows its designed tile.
   With a v0.17 home.json the counts are unknown and not shown.
3. **주요 프로젝트.** A lead project (it needs a photo of at least 960 px) and four beside it.
4. **전시 · 축제 · 미디어아트.**
5. **답사 코스.** The curated Seoul courses.
6. **세계의 미디어파사드.** A quieter strip of six, on a panel band, with a link to `#world`.
7. **About** (이 아카이브에 대하여).

Cards carry `data-country`, and the spec checks that at least 70 % of the projects on the home page are Korean.

### home.json v0.18 (what the app reads)

```jsonc
{
  "schema": 1, "build_id": "…", "generated_at": "…",
  "counts": { "projects": 274, "countries": 30, "with_images": 140, "kr": 50, "world": 224 },
  "hero": [ { "project": "<id>", "image": { /* a v0.18 image object, tier 1–2, approved: true */ } } ],
  "kr_regions": [ { "key": "seoul", "count": 30, "project": "<id>", "image": { /* tier ≤ 3 */ } } ],   // all eight, in order
  "kr_featured": [ "<id>", … ],      // Korean facades and the like
  "kr_programs": [ "<id>", … ],      // exhibitions, festivals, media art, light festivals, nightscape
  "world": { "count": 224, "highlights": [ "<id>", … ], "regions": [ { "key": "europe", "count": 162 } ],
             "countries": [ { "key": "DE", "count": 104 } ] },     // a plain list of ids is read as highlights
  "projects": { "<id>": { /* compact record: id, names, country_iso2, kr_region, city, lat, lng, project_type,
                           year, shard, image */ } }
}
```

The v0.17 keys (`featured`, `regions`, `types`, `themes`, `recent`) are still read. When `kr_regions`, `kr_featured`,
`kr_programs` and `world` are all absent, the app regroups the v0.17 picks Korea first:

- Korean hero photos;
- region tiles from the Korean projects home.json carries;
- Korean picks in the featured and programme sections;
- foreign picks in the world strip.

The live dataset had this shape on 2026-10-25.

## Images

`client/dataset-rows.mjs` reads every image object of the v0.18 addendum, and also the older shape:

- **Identity and source:** `provider` is kept as `image_provider` and shown in credits.
- **Sizes:** `display` sizes are kept only up to the original's width and only over https. `thumb_w` and `thumb_h`
  come from index rows.
- **Rights:** `rights_holder` and `usage`.
- **Verdict and tier:**
  - `approved: false` and tier 6 are dropped.
  - The six v0.18 tiers fold onto the app's four card tiers: 1 → 1, 2 → 2, 3 and 4 → 3, 5 → 4 (context).
  - `role: context` marks a context photo.

Each photo gets its **renditions**, `[[width, url], …]` in ascending width:

1. the provider's display list;
2. otherwise Commons standard widths (330, 500, 960, 1280, 1920, 3840; https://www.mediawiki.org/wiki/Common_thumbnail_sizes),
   always below the original's width, derived from the file URL;
   - query strings (the live data carries `?utm_…`) and `<w>px-thumbnail.<ext>` names are handled;
   - a Commons original of 1280 px or less is also its own largest size;
3. otherwise the thumbnail and the original at their known widths.

With an unknown original width, nothing is offered above the thumbnail the source gave. The live hero used to load its
500 px thumbnail because the query string broke the Commons parser. It now offers up to 3840 px.

**Slots** (`app.js` `SLOT_MIN`). A photo fills a slot only if its largest rendition reaches the slot's minimum:

| slot | minimum largest rendition |
|---|---|
| hero | 1600 px |
| lead | 960 px |
| tile | 480 px (a 500 px index thumbnail fills a region tile; v0.18 card thumbnails are about 640 px) |
| card | 320 px |
| row | 120 px |

Small slots also take a photo of unknown size (a provider thumbnail). Otherwise the next photo of the project is used,
then the designed placeholder of its type. There is no code path that puts a small thumbnail into a large slot.

On a place page:

- The lead photo is the first in gallery order that fits the lead slot.
- A smaller photo is shown at its own size on a dark mat (`.matted`), never stretched.
- Gallery figures are never wider than their largest rendition.

Every `<img>`:

- has a `srcset` of its renditions, `sizes` from the layout, and width and height from the original (an aspect-ratio
  box, so nothing shifts);
- uses the focal point as `object-position` when the dataset has one, else the centre;
- is lazy below the fold, and `fetchpriority=high` on the first screen's photo;
- is always `decoding=async`.

On a load error a photo is tried once more at a smaller rendition. After that it becomes the designed placeholder of
the project's type (`.ph.ph-<type>.ph-failed`): never a broken box, and never a retry loop. Failed world-map tiles are
hidden.

**Formats.** `<picture>` with AVIF and WebP `<source>`s is used only where the provider serves the same image in those
formats on request. Today that is Unsplash (images.unsplash.com, imgix's `fm` parameter).

- Commons, Flickr, Openverse, TourAPI and KTO serve the original's format, so their photos keep a plain JPEG
  `srcset`.
- Nothing is converted or rehosted.
- `picture{display:contents}`, and every `>img` rule has a `>picture>img` twin.
- On an error the `<source>`s are dropped before the smaller retry, and the whole `<picture>` becomes the placeholder.

**Detail page on a phone** (verify-live's mobile-detail LCP was 1712 ms against 136 ms on v0.17). At 390 px and 2× the
lead photo loads the 960 px rendition for its 780-device-pixel slot. The next size down, 500 px, would be soft; v0.17
showed that 500 px thumbnail. So the rise is the price of a sharp photo, plus the gallery's photos competing with it:
they all sit within Chromium's lazy-load distance on a phone. To reduce that competition:

- gallery photos are `fetchpriority=low`;
- the gallery is `content-visibility:auto` (14 photo requests became 7 on the live-data page);
- `index.html` preconnects to upload.wikimedia.org, since the lead photo's address is known only after the script runs.

**Credits.**

- On cards and tiles the credit is quiet: a small one-line chip, still a 44 px target.
- The hero plate names author · licence · provider.
- The gallery gives author and licence, 출처 (provider) and 권리자 (rights holder), with links to the original and the
  licence.
- Daytime architecture photos are labelled 건축 맥락 사진 in the gallery. They never appear on the home page or above a
  media-active photo on a card.

## Search engines and link previews

The app routes with the URL fragment (`#place/<id>`). Crawlers and link-preview scrapers (Naver, Kakao, Facebook,
X) never see fragments. So the deploy writes plain HTML pages from the dataset with `scripts/prerender.mjs`.

| output | what it holds |
|---|---|
| `p/<dataset id>/index.html` | one page per project of `index.json` (details below) |
| `p/index.html` | every project: Korean ones by region, then the rest by country |
| `sitemap.xml` | the site's own pages plus all of these, with `lastmod` from `added_at` |
| `<meta name="aol-static-pages">` in `index.html` | the marker the app reads (below) |

A project page holds:

- **Meta.** Title (`name · city district · 빛의 건축`), description, canonical, and OG and Twitter meta. The OG image is
  the lead photo's rendition nearest 1200 px; without a photo it is the site image.
- **JSON-LD.**
  - A `CreativeWork` with its place, coordinates, `sameAs` and credits.
  - Every photo as an `ImageObject` with creator, `license`, `acquireLicensePage` and `creditText`.
  - A `BreadcrumbList`.
- **Content.**
  - The lead photo with its renditions (`srcset`), never wider than its largest one, with author · licence · provider
    · 원본 보기.
  - Facts, the summary, up to six more credited photos, sources, and other projects of the same region.
  - A link into the app.

No script runs on these pages. The description is the record's own summary, or else a plain statement of what the
record holds; nothing is invented. Text is HTML-escaped, and JSON-LD escapes `<`, `>` and `&`. Photos come from the
app's readers (`client/dataset-rows.mjs`), so nothing the app would reject is printed.

The app points its canonical link, its description and shared links at `p/<id>/` only when `index.html` carries the
marker. Without the marker (no pages deployed) nothing links to a page that does not exist. Curated places with a
dataset record use that record's page. The service worker never answers `p/` with the app shell.

robots.txt (with its `Sitemap:` line), and canonical and OG meta on the app and the static pages, come from
`scripts/build.mjs` as before. `pipeline/deploy.mjs` adds `Disallow: /data/admin/`.

**Wiring (pipeline track).** The preferred wiring: `pipeline/deploy.mjs` calls
`prerenderSite(datasetFiles, tree)` on the dataset it actually publishes, so pages never come from a rejected dataset.
The function is exported and pure. `datasetFiles` is the files map `loadDataset` returns. `tree` is the built site,
a map of path to Buffer. The function returns a map of path to string: the files to add or replace, which are `p/…`,
the merged `sitemap.xml`, and `index.html` with the marker. The site URL comes from the canonical link of
`index.html`, or from `{siteURL}`.

```js
import { prerenderSite } from '../scripts/prerender.mjs'
// after the dataset files are in the tree (the fresh or the kept one):
try { for (const [p, s] of prerenderSite(datasetUsed.files, tree)) tree.set(p, Buffer.from(s)) } catch (e) { log(`no project pages: ${e.message}`) }
```

The minimal alternative is a step in `archive.yml` between "Build the site" and "Assemble main":

```sh
node source/scripts/prerender.mjs --dist=source/dist --data=data/site-data --site-url="$SITE_URL"
```

Run this way, a dataset that cannot be read leaves `dist/` as it was, and the site deploys without `p/`.

Size on the live dataset (274 projects): about 8 KB per page (5–36 KB), 3.6 MB in all. With the `_headers` CSP
(`script-src 'self'`) none of the 275 pages reports a violation: the JSON-LD block is data and never runs.

Tests: `tests/prerender.test.mjs` (pages, escaping, unlicensed photos, list page, sitemap merge, CLI) and
`qa/seo.spec.mjs`. The spec covers axe and no sideways scroll at 390 and 1440 px in light and dark, the photo and the
link into the app, and the canonical and share links with and without the marker.

## Fixes along the way

- **Endless re-render.** `client/dataset.js` `ensureIndex()` published, and so re-rendered, before storing its run. A
  curated place page with an archive record asks for that record, the record asks for the index, and the index
  re-entered `ensureIndex()` forever: a hung page at 100 % CPU, on the live site as well. The run is now stored first.
  `qa/v18.spec.mjs` guards it.
- **Bare dataset ids.** `#place/<dataset id>` without `AR-` showed "not found". It now opens the project.
- **Account module only with a server.** `index.html` loads `assets/cloud-boot.js` (124 bytes). It imports
  `assets/cloud.js` (with the Supabase client, about 180 KB) only when `config.js` names a server. The static site
  never downloads it, and the account page then says 기기 내 저장. `qa/archive.spec.mjs` checks both cases.
- **About page.** `about.html` describes the Korea-first sections and the photo rules.
